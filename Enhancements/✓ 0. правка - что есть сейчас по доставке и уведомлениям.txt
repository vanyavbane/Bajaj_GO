# Промпт: переработка остановок ресторанов и позиционирования уведомлений в bajaj GO

> Ты — опытный Three.js-разработчик (r160) и геймдизайнер. Тебе дан рабочий файл **`bajaj-go.html`** (voxel-раннер в духе Traffic Rider: физика, HUD, экономика с топливом/износом/доставкой, сохранения, тюнинг, камеры, трафик, прыжки, погода, постобработка, меню, гараж, магазин).  
> Задача этого этапа — **точечные правки двух механик**: (1) остановки ресторанов и (2) позиционирование всплывающих уведомлений.  
> Верни **один полный HTML-файл целиком**. Не фрагмент, не заглушку. Не ломай существующие механики.

## Часть 1. Остановки ресторанов — отдельные точки, а не одна «зона ресторанов»

### Что сейчас
Сейчас в системе экзитов (`E`, `le()`, `Ae()`, `Oe()`, `R()`, `he()`, `ce()`, `xe()`, `Te()`, `Ye()`) есть общий тип `"restaurant"`, и при въезде в зону ресторана открывается **общее меню со списком ресторанов** `M = [{name:"McDonald's"}, ..., {name:"Пицца Хат"}]` (функция `Ye()` строит список `vl({...})` по всем ресторанам из массива `M`). То есть одна остановка = выбор любого ресторана из списка.

### Что нужно
Сделать так, чтобы **каждый ресторан из массива `M` был отдельной остановкой** со своим логотипом, названием, бейджем и попапом.

### Требования

1. **Убрать общий тип `"restaurant"` из пула экзитов.** В массиве `b = ["restaurant","fuel","sto","tuning"]` убрать `"restaurant"` → остаётся `["fuel","sto","tuning"]`, плюс добавить **отдельные типы** для каждого ресторана. Проще всего — ввести динамические ключи: `rest_0`, `rest_1`, …, `rest_6` по индексу в `M`. Итоговый пул: `["fuel","sto","tuning","rest_0","rest_1","rest_2","rest_3","rest_4","rest_5","rest_6"]`.
   - Проверить `he()` — он возвращает тип для следующей остановки с учётом активного заказа и приоритетов. Логику приоритета (`fuel` → если нет заказа, предложить ресторан → `sto` → `tuning`) **сохранить**, но вместо строки `"restaurant"` возвращать **случайный `rest_N`** из тех, что ещё не были на дороге впереди (или просто случайный из `M`). Если у игрока уже есть активный заказ (`y`), приоритет `fuel` → `sto` → `tuning` — `rest_*` не предлагать, пока заказ не выполнен (это уже логика текущего `he()`, сохранить).
   - При `used === true` (после въезда) остановка всё равно уходит в рециркуляцию через `Oe()` — это не менять, только тип должен рециркулироваться как `rest_N`.

2. **Свои текстуры для каждого ресторана.** Сейчас `B(type, dir)` рисует один универсальный баннер по `w[type]` (объект `w` с `restaurant/fuel/sto/tuning`). Нужно:
   - Для каждого ресторана `M[i]` (McDonald's, Вкусно — и точка, KFC, Burger King, Суши Wok, Додо Пицца, Пицца Хат) сделать **свою текстуру** баннера с названием и бейджем ресторана (используй `M[i].name` и `M[i].badge`; при желании — фирменный цвет: `#ffcc00` для McDonald's/Вкусно, `#e4002b` для KFC, `#d62300` для Burger King, `#ff6b00` для Суши Wok, `#ff5a00` для Додо, `#e4002b` для Пиццы Хат — на твой вкус, главное чтобы читалось).
   - Кэш: `$` (объект) сейчас хранит `right/left` для 4 типов. Расширить так, чтобы `$["rest_0"].right` и т. д. — тоже работали. То есть генерировать `B("rest_" + i, 1)` и `B("rest_" + i, -1)` для каждого `i ∈ 0..6`.
   - Иконки-спрайты `$e.icons[type]` — сейчас есть `icons` для `restaurant/fuel/sto/tuning`. Для `rest_N` — тоже сгенерировать свою иконку (эмодзи + бейдж + фирменный цвет) через `Ue(type)` (аналог `Ue("restaurant")`, но с уникальным эмодзи/цветом на каждый ресторан). Эмодзи: 🍔 для McDonald's/Вкусно/BK, 🍗 для KFC, 🍣 для Суши Wok, 🍕 для Додо/Пиццы Хат.
   - Лейблы-спрайты `$e.labels[type]` — генерировать `W("rest_" + i)` со названием ресторана (сверху) и «ДО 50 КМ/Ч» (снизу). Функция `W(L)` сейчас жёстко берёт `q[L]` — заменить/переопределить, чтобы для `rest_N` брала `M[i].name`.
   - Иконки `k`, названия `q` (объекты) — для `rest_N` генерировать динамически (Map или отдельный объект), не хардкодить.

3. **Меню при въезде в конкретный `rest_N`.** Функция `Ye(L)` сейчас рисует список всех ресторанов. Нужно:
   - Передавать в `Te(L)` тип остановки (`L.type`, например `"rest_2"`).
   - В `Ye(type)` определять индекс ресторана по типу (`i = Number(type.slice(5))`), брать `M[i]`, и показывать **карточку именно этого ресторана**: логотип/бейдж, название, «Взять заказ на доставку» (кнопка), описание «Съезд · доставка еды», если заказ уже активен — показать `Xt` «Активный заказ: …» и заблокировать кнопку.
   - Если у игрока уже есть заказ (`y`) — **все** `rest_N` показывают то же, что и сейчас общий ресторан: `Xt` с активным заказом + список ресторанов заблокирован. Логику «нельзя взять второй заказ» сохранить, но меню теперь по одному ресторану.
   - Кнопка «Взять заказ» вызывает существующий `ut(M[i].name)` — не менять `ut()`, он уже принимает имя. После успеха — `Ne()`, `P(...)` — как сейчас.
   - Убедиться, что после взятия заказа **остальные** `rest_N` на дороге остаются, но при въезде в них меню будет показывать «Активный заказ: …» и блокировать кнопку (это поведение уже есть для общего ресторана, сохранить для каждого).

4. **Маркер/зона остановки.** Функция `xe()` создаёт маркер с `$e.icons.restaurant` и `$e.labels.restaurant`. Нужно параметризовать: `xe(type)`, где для `rest_N` берутся иконка и лейбл именно этого ресторана, для `fuel/sto/tuning` — как сейчас. В `le()` вызов `const T = xe();` заменить на `const T = xe(type)` — но `le()` сейчас не принимает `type`. Придётся либо передавать тип в `le(type)` из `mt()` (там, где создаётся пул `E` в цикле `for (let L = 0; L < m; L++)`), либо создавать маркеры лениво/пересоздавать текстуру при смене типа. Рекомендуемый путь: в `mt()` в цикле инициализации для каждой из `m = 5` остановок сразу назначить `type` из `b` (например, по `L % b.length`) и передать в `le(type)`, который создаст соответствующий маркер. Дальше `ce(exit)` уже обновляет `signMat.map`, `iconSprite.material.map`, `labelSprite.material.map` при смене типа — **доработать `ce()`**, чтобы он корректно брал `$`/`$e.icons`/`$e.labels` для `rest_N`.

5. **Что убрать.** Общий тип `"restaurant"` больше не должен появляться нигде: ни в `b`, ни в `w`, ни в `$e.icons`, ни в `$e.labels`, ни в `$`, ни в `q`, ни в `k`, ни в `I` (`I = { food: 3989629, service: 16765514 }` — цвет зоны; для `rest_N` использовать `I.food`). Убрать общую иконку «🍔 РЕСТОРАНЫ» и общий баннер.
   - Функция `he()` не должна возвращать `"restaurant"`.
   - В `B(type, dir)`, `Ue(type)`, `W(type)` — не должно быть ветки `type === "restaurant"`, только `rest_0..rest_6`.

6. **Совместимость и сохранения.** Активный заказ `y` хранится в `localStorage` с полем `restaurant` (имя), а не типом — это менять **не нужно**, имя не ломается. При въезде в `rest_N` проверять `y && y.restaurant === M[i].name` — если да, показать «Заказ этого ресторана уже активен», иначе — «Активный заказ: …» (как для любого другого ресторана).

## Часть 2. Позиционирование всплывающих уведомлений (event-feed)

### Что сейчас
`i.pushFeed(text, kind, value)` (функция `x` внутри `f0()`) добавляет элемент в `#event-feed`, а `#event-feed` в CSS позиционирован **по центру**:
```css
#event-feed{position:fixed;top:34%;left:50%;transform:translate(-50%);width:min(440px,92vw);...}
```
Поэтому уведомления «Комбо ×N» и «Перелёт ×N» (а также «Жёсткая посадка», «+рубли» и т. д.) появляются в центре и перекрывают дорогу.

### Что нужно
Выводить уведомление **с той стороны, где была машина трафика** (или где произошло событие):
- Машина/событие справа → уведомление справа (прижато к правому краю).
- Машина/событие слева → уведомление слева.
- Событие по центру / «прыжок» / «посадка» / общие сервисные сообщения (тюнинг, топливо, заказ доставлен) → можно оставить по центру, но сдвинуть **вверх** (например, `top: 18%`), чтобы не закрывать дорогу и HUD с показателями.

### Требования

1. **Прокинуть сторону в `pushFeed`.**
   - Сейчас `pushFeed(text, kind, value)` вызывается из `updateTraffic` (`A === "overfly"`, `A === "near"`, `A === "crash"` — crash не пушит, а `handleAccident`), `a()` (жёсткая посадка / прыжок), `Ge()` (тюнинг), `ze()` (ДТП), `Ne()` (пауза), `O()`/`ye()` (СТО) — то есть из многих мест.
   - Добавить в `pushFeed` **пятый аргумент `side`** (`"left" | "right" | "center"`, по умолчанию `"center"`). Не менять существующие вызовы (они остаются `center`).
   - В `updateTraffic` для событий `"near"` и `"overfly"` вычислить сторону: `side = (m.lateralOffset < i.laneOffset) ? "left" : "right"` (или по знаку разницы — если машина левее игрока, уведомление слева). Для встречки (`laneIdx < 2`) — тоже по позиции.
   - В `a()` (посадка/прыжок) — `side = "center"`.
   - В `Ge()`, `ze()`, `O()`, `ye()`, `Ne()` — `side = "center"`.

2. **CSS: три позиции.**
   - `#event-feed` по умолчанию — центр, но сдвинуть вверх: `top: 18%` вместо `34%` (чтобы не закрывать дорогу внизу и не перекрывать `#eco-hud`/`#tp-hud`).
   - Добавить классы:
     - `.feed-left { left: 3vw; right: auto; transform: none; align-items: flex-start; }`
     - `.feed-right { right: 3vw; left: auto; transform: none; align-items: flex-end; }`
     - `.feed-center { left: 50%; right: auto; transform: translateX(-50%); align-items: center; }`
   - На мобильных (`@media (max-width: 700px)`) — `left/right: 2vw`, `top: 12%` (под шапкой), ширина `min(70vw, 320px)`.
   - Элементы `.feed-item` внутри — выравнивание по соответствующему краю; сохранить существующую анимацию `feedLife` и `frozen` (пауза при `i.uiModal || i.paused` — уже реализована через `.frozen`).

3. **HTML: разделить на три контейнера (рекомендуемый путь).**
   - Вместо одного `#event-feed` использовать три: `#event-feed-left`, `#event-feed-center`, `#event-feed-right`.
   - `pushFeed` выбирает контейнер по `side`. Внутри ведёт отдельный счётчик `c` (сейчас один массив `c` в `f0()`), либо один общий массив `c` с полем `side`, а при удалении элемента — удалять из правильного контейнера (проверять `el.parentNode`).
   - `clearFeed` чистит все три.
   - `tickFeed` обходит общий массив `c` (проверяет `life`), удаление — из `el.parentNode`.
   - `frozen` — применять ко всем трём контейнерам (или по одному разу на контейнер, если они все одновременно «замораживаются»).
   - Альтернатива (проще): один `#event-feed`, но при добавлении элемента — добавлять класс `feed-left/right/center` на **сам элемент** `.feed-item` и позиционировать сам элемент через `align-self`. Тогда контейнер `#event-feed` остаётся по центру сверху, но элементы выстраиваются слева/справа/по центру внутри него (ширину контейнера придётся расширить до `100vw`, чтобы левый и правый края были достижимы). Этот вариант **предпочтителен** — меньше правок в `f0()`, `clearFeed`, `tickFeed`, `frozen`.

   **Рекомендация:** реализовать через классы на `.feed-item`:
   - `#event-feed { position: fixed; top: 16%; left: 0; right: 0; width: 100vw; display: flex; flex-direction: column; pointer-events: none; z-index: 12; gap: 6px; padding: 0 3vw; }` (без `transform`, без `left: 50%`).
   - `.feed-item { max-width: min(440px, 60vw); }`
   - `.feed-item.side-left { align-self: flex-start; }`
   - `.feed-item.side-right { align-self: flex-end; }`
   - `.feed-item.side-center { align-self: center; }`
   - На мобильных — `max-width: 70vw`, `padding: 0 2vw`, `top: 12%`.

4. **Обновить `pushFeed` (функция `x` в `f0()`).**
   - Сигнатура: `function x(P, B, $, side = "center")` — не ломать существующие вызовы `x(text, kind, value)` (третий аргумент остаётся `value`, четвёртый — `side`).
   - При создании `q.className = "feed-item " + I + " side-" + side;`.
   - Остальное (жизнь `o = 2.6`, максимум `d = 6` элементов, `c.push({el, life})`) — не трогать.

5. **Обновить вызовы в `updateTraffic` (`o()` в `bg()`).**
   - Для `"overfly"`: `i.pushFeed("ПЕРЕЛЁТ ×" + C, "overfly", C, (m.lateralOffset < i.laneOffset ? "left" : "right"))`. Учесть, что `m.lateralOffset` — текущее смещение трафика; если машина левее — уведомление слева.
   - Для `"near"`: `i.pushFeed("КОМБО ×" + i.comboCount + " · +" + C + " ₽", "combo", i.comboCount, (m.lateralOffset < i.laneOffset ? "left" : "right"))`.
   - В `a()` (посадка): `i.pushFeed(M, v ? "hard" : "land", _, "center")`.
   - Остальные (`Ge`, `ze`, `O`, `ye`, `Ne`) — `"center"` (по умолчанию, менять не обязательно, но лучше явно передать `"center"` для читаемости).

6. **Проверить, что уведомления не перекрывают HUD.**
   - `#eco-hud` — `top: 82px; left: 20px`.
   - `#order-hud` — `top: 12px; left: 50%`.
   - `#status-badges` — `top: 70px; right: 20px`.
   - `#jump-live` — `top: 23%; left: 50%`.
   - `#tp-hud` — `right: 20px; bottom: 82px`.
   - При `top: 16%` и высоте элементов ~40px с 3–4 элементами стопка займёт ~200px, то есть до ~36% экрана. На узких экранах — не перекрывает `#order-hud` (он сверху по центру) и `#status-badges` (справа сверху), но **может** приблизиться к `#eco-hud` при `left`. Проверить на `@media (max-width: 700px)`: `#eco-hud` узкий (`width: 172px`), уведомления слева — `padding: 0 2vw`, `max-width: 70vw`. Если пересекаются — сдвинуть `#event-feed` на `top: 14%` или ограничить высоту стопки (`max-height: 40vh; overflow: hidden`), но лучше просто не давать стопке разрастаться (лимит `d = 6` элементов уже есть, при 2.6 с жизни это редко больше 3–4 одновременно).

7. **Не ломать `frozen`.**
   - Сейчас `x()` добавляет/снимает класс `frozen` на `#event-feed`, чтобы при паузе/модалке анимация не «тикала». При переходе на один контейнер с классами на элементах — `frozen` остаётся на `#event-feed`, поведение сохраняется. `M(P)` (tickFeed) тоже не меняется.

## Чек-лист перед выдачей

1. Каждый ресторан из `M` — отдельная остановка со своим баннером, иконкой, лейблом, названием, бейджем.
2. Общий тип `"restaurant"` удалён из `b`, `w`, `$`, `$e.icons`, `$e.labels`, `q`, `k`. Нигде не всплывает.
3. При въезде в `rest_N` открывается меню **этого** ресторана с кнопкой «Взять заказ». Если заказ уже активен — блокировка и сообщение.
4. `ut(name)` работает как раньше, заказ сохраняется в `localStorage` с именем ресторана.
5. `he()`, `Ae()`, `Oe()`, `ce()`, `xe()`, `le()`, `mt()` — корректно работают с новыми типами `rest_N`.
6. `updateDeliveryMarker` (`fe()`), `V` (маркер заказа) — работают без изменений (они завязаны на `y.targetS`, а не на тип).
7. `pushFeed` принимает `side` и корректно позиционирует уведомление слева/справа/по центру.
8. Уведомления «Комбо» и «Перелёт» появляются с той стороны, где была машина.
9. Общие уведомления (тюнинг, посадка, топливо, пауза) — по центру, но `top: 16%` вместо `34%`.
10. `frozen` (пауза/модалка) — работает.
11. На мобильных (`@media (max-width: 700px)`) уведомления не перекрывают `#eco-hud`, `#order-hud`, `#status-badges`, `#tp-hud`, `#jump-live`.
12. Все прежние механики (физика, HUD, экономика, доставка, сохранения, тюнинг, камеры, погода, постобработка, меню, гараж, магазин) — не сломаны.
13. Файл запускается, консоль чистая.

**Верни полный HTML-файл целиком.** Не фрагмент, не заглушку. Если после генерации что-то не работает — перегенерируй файл целиком, не правь фрагментами.
